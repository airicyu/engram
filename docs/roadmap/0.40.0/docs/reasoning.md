# 0.40.0 reasoning

做什麼以 [INDEX](../INDEX.md) 為準。本檔只留動機與反例。若要改已定案，須先能回答「原本要防的失敗模式是否仍成立」。

## 為何掛 Memory 第三 mode，不是第五左欄

0.36 把工作台收成四項循環：事件／尋問／提問郵箱／記憶。未來視是 **已沉澱的前瞻錨**，與鏈（過去敘事）、節點（主題理解）同層：都是「進去記憶裡翻」。獨立左欄會讓人以為未來視是另一種工作（像尋問或釐清），並打破「記憶＝長期庫瀏覽」的殼。

失敗模式：左欄變成五個平權入口，事件頁與記憶頁的分工重新變糊。

## 為何不掛在 Seek

Seek 是問句驅動：關鍵字撞上、或 Ask 合成回答。未來視瀏覽的需求是 **無問句掃窗內有什麼**。塞進 Seek 會變成「先搜才看得到清單」，或把搜索頁加成第三欄，兩者都不是尋問。

Search／Ask 命中改成深鏈進瀏覽頁：問句路徑與掃讀路徑接上，但不把掃讀主畫面放在 Seek。

## 為何不新 API

`GET /memories/future-sight` 已含每則 `content` 與排序（hot 近→遠，再 later）。前端一次 GET 就能做列表＋正文。新 `GET …/{id}` 會逼 server 再維一套「單則」契約，卻幾乎沒有比陣列 find 更多的語意。

失敗模式：為 UI 方便發明 detail path，phases 與 api-docs 膨脹，行為仍等於現有陣列。

## 為何列表分組而不是單一時間線

產品把窗切成 hot（預設 30 天）與 later（其餘至 window）。混成一條「全部按 start 排」會讓人以為只有遠近、沒有兩區政策；也與 GET 陣列順序（先全部 hot）不一致，UI 還得重排。

否決「第二列 pill 只看 hot 或只看 later」：多一次點擊才能對照兩區；空 later 時 pill 還要殘廢。組標題在同一捲動裡對照即可。

## 為何不展示 swept_expired

GET 的 expire-only 是維護副作用，不是瀏覽功能。做 toast／「本頁剛清掉 N 則」會讓翻閱頁看起來像維運台，且每次進頁都可能閃一次。過期進 L0 系統事件，人若要知道走事件頁。

## 否決

| 方案 | 為何不選 |
|------|----------|
| 第五左欄 | 破 0.36 四項殼 |
| Seek 內主列表 | 把掃讀做成搜索的附屬 |
| 人手編輯錨 | 無寫 API；編輯器是另一題 |
| 日曆／甘特 | 錨是短文檔點，不是行事曆產品 |
| 本版一併做橫向鏈 | 正交；見 backlog strip |
| 抬 boot／新 hop | 無新目錄 |
