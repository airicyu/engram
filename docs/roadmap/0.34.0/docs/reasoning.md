# 0.34.0 — Reasoning（WHY）

← [INDEX](../INDEX.md)

> **做什麼以 INDEX 為準。** 本檔只留動機與對 0.18 的推翻。若要改已定案，須先能回答「原本要防的失敗模式是否仍成立」。

## 0.18 為何要使用者勾選 later

當時假設：Ask 用 AI 讀檔，later 在 window=365 後可能累積較多停泊項，token／延遲成本高；問句形態又分不出落點在過去／hot／later。因此預設只開 hot，較遠錨點交給人顯式 `include_later`。並否決「兩段式找不到再讀 later」（弱命中會早停）。

## 為何本版推翻旗標、不推翻「不要兩段式」

產品判斷已變：未來視內容不細、量不大，Ask 讀兩檔的成本可接受。人當閘門的成本反而更高——漏勾就漏一年窗內的正確檔期。

**選定：** 每個 job **一開始**就把 later 放進可讀 map（與 Search 掃兩區對齊）。由 **同一個蒐證輪**的 agent 決定開不開 later、引用哪些錨點。

這不是 0.18 否決過的「server 依問句分類 zone」，也不是「先答完再偷偷開 later」。失敗模式「弱命中早停」在兩檔都已允許時不成立：agent 若認為問題可能涉及較遠計畫，應在同一輪讀 later，而不是等第一段失敗。

## 為何廢欄而不是忽略欄

若靜默忽略 `include_later: false`，舊客戶端以為自己關掉 later，實際已可讀——語意謊言。與 0.32 廢 `node_refs` 相同：鍵在 → **400** `include_later_removed`，逼客戶端改成只傳 `q`。

## 否決項

| 方案 | 為何否決 |
|------|----------|
| 保留勾選、只改預設 on | 人仍在當閘門；workflow 未簡化 |
| 靜默忽略舊欄 | `false` 的語意會騙過舊客戶端 |
| 兩段式自動升級 | 0.18 早停失敗模式仍在 |
| Server 問句路由 zone | 問句不可辨；與「交給 AI」重複且更脆 |
| 合併 hot／later 檔 | 非本版問題；browse／分桶仍有用 |
