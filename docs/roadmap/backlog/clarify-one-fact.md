# 釐清：一題一事實，答了就要吸收

**狀態：** 構想。尚未排進版本。

## 題意

`engram-clarify-generate` 每次 distill 後強制新建 3–5 題。題幹常把兩三個可分開的事實寫進同一題；人只答其中一句，其餘在吸收時消失。已答的 `clarify/pending/` 可以跨過下一次沉澱仍留著，等於答過但沒進鏈、也沒進節點。`asking/` 被清空不代表問題被用掉。

要做成：

- 一題只問一個能寫進某個 day 或某個 node 的事實（誰、何時、是否、一個數字或一個決定）。題幹點出已知上下文，但問句只有一個。
- 沒有新事件、也沒有未解的節點矛盾時，這次 clarify-generate **跳過**，不要為了湊滿 3 題而出題。配額 3–5 只在確有可問的缺口時當上限，不是下限。
- 下一次 distill 對 `clarify/pending/` 的每一題必須收斂：寫進 chain／node 後移到 `history/`（可加 `absorbed_at`），或標明捨棄原因後移到 `history/`。不准原封留在 `pending/`。
- 答案只覆蓋題目的一部分時：寫下答到的那一事實，其餘不要發明；該題仍算已吸收，不要為了沒答到的子句再開同一題。

## 可能要定（排進版本時寫進 INDEX）

- 「沒有可問的缺口」由 skill 判斷並在 job 裡寫一句原因。Program 只保留現有的「無事可沉澱則跳過生題」；不要在 server 再寫一套該問什麼。
- 捨棄原因要不要進 history frontmatter（例如 `dismissed_because`）。短、機械即可。
- 同一缺口若人已答過又被重問，算失敗。驗收用虛構 fixture：一題兩問、只答半句、pending 留到下一次 distill。

## 不要當成題目的一部分

- 把出題規則寫成 TypeScript 分類表
- 提高或維持「每次至少 3 題」當產品要求
- 讓 Ask 讀 `clarify/`
- 用釐清題填補整日沒有日記的空洞（見 [進行中的週記](./chain-open-period.md)）
